# Spyglass — Architecture Plan
### A content-aware shot search app for Rough Cut Studio Suite

## 1. Purpose and Scope

Spyglass is one of eight apps in Rough Cut Studio Suite: Card Eater, A-Sync, Local Interview Transcriber, B-Roll Analyzer, Rough Cut Studio, Harmonizer, Blair Brander, and Spyglass. Card Eater ingests and verifies raw footage off camera cards, Local Interview Transcriber generates speech transcripts, and B-Roll Analyzer scores b-roll clips on technical quality (not subject matter — see Section 3, this was a wrong assumption in an earlier draft of this plan). None of the three produces the kind of subject-matter tag ("mascot," "studying," "cheering") that makes footage findable by what's actually in frame. Spyglass is that layer: type "students studying in the library" or "mascot cheering at a football game" and get back the specific shots, cued to the right timecode, from years of archive.

It is not another ingestion pipeline. It is a shared index and a search UI that sits on top of the metadata the other apps already produce, and fills in gaps where that metadata doesn't exist yet. It's also the natural place to build a **selection pool**: check off shots from search results, then hand that pool straight to Premiere Pro as an editable sequence, skipping the manual re-import/re-cutting step entirely.

Everything here stays on the machine. No frames, transcripts, or metadata leave the local disk — required both by the "no cloud, no student data off-device" mandate and because the archive is large enough that cloud round-trips would be slow and expensive anyway.

## 2. Requirements

**Functional**
- Natural-language search ("mascot cheering," "kids studying outside") returning ranked shot results with thumbnails and timecodes.
- Tag/facet search — browse by category (event type, location, subject, sport, season, shot type) without typing a query.
- Visual similarity search — "find more shots like this one," starting from a frame already in the results or from the current NLE timeline.
- Combined/hybrid search — a text query narrowed by facets (e.g., "cheering" + tag:mascot + date range: Fall 2025).
- Jump-to-source: every result opens directly in the source clip at the right timecode, or can be sent to the active NLE timeline.
- Selection pool: multi-select shots across any number of searches into a working pool, then export that pool either as a Premiere Pro-importable sequence (see Section 14) or as a consolidated, optionally-trimmed copy of the underlying media in a single destination folder (see Section 15) — rather than manually relinking or hunting down each clip.
- Handoff-friendly: a coworker can run their own install against the same archive and get the same search experience, without requiring a shared server (see Section 11).
- Point-and-forget indexing: aim the app at one or more root folders and have it recursively discover, segment, tag, and embed everything inside — including footage the other three Suite apps have never touched — with no per-file manual step (see Section 7), scoped to an explicit allowlist of approved drives/folders (see Section 8).
- Works incrementally — newly ingested/transcribed/tagged footage should appear in search without a full archive re-index.

**Non-functional**
- Fully offline; no third-party or cloud APIs.
- Archive scale: tens of thousands of clips, growing every season — index and query performance must not degrade linearly with naive scans.
- Indexing runs in the background/at idle, never blocking an active edit.
- Indexing is resumable — an interrupted index job (laptop closed mid-run) picks up where it left off.
- Tolerant of partial/missing metadata, since the three source apps don't uniformly produce the same outputs today.
- Tolerant of drives coming and going: search results stay usable when a source drive is disconnected, and an unplug mid-index is a clean pause, never a corrupted job or a stuck queue (see Section 9).
- Local cache footprint stays modest and user-controllable — capped keyframe size, quantized embeddings, and a configurable size limit with eviction, rather than growing unbounded with archive size (see Section 10).
- Scoped by default to nothing — indexing and search only ever touch drives/folders explicitly allowlisted by the user, never the whole filesystem (see Section 8).

**Constraints**
- Built by one person (you), so favor low-maintenance, single-binary/local-service architecture over anything requiring its own ops (no standalone servers to babysit).
- Must fit the existing Suite conventions: local-first, dark mode, Blair Athletic Blue/Warm Grey/Cool Grey palette, native desktop shell (Tauri — Rust core + OS-native webview, chosen over Electron for footprint and native OS integration; see Section 16), SQLite for structured data.
- ML/indexing pipeline (CLIP embeddings, VLM captioning, scene detection) runs as a local Python sidecar process the Rust core shells out to — keeps the native shell thin without forcing the ML pipeline into Rust.
- Ships standalone (its own Tauri app, matching Card Eater's precedent), with an explicit later embed into Studio Suite's unified window in view — see Section 19. That means core logic (adapters, indexing pipeline, search API) belongs in a Rust library crate kept separate from the Tauri-shell binary, so the embed is a wiring change later rather than a rewrite.

## 3. Verified Upstream App Outputs

This section was originally written from assumptions (flagged explicitly as such) since I didn't have access to the other three apps' actual code. That access has since been granted and the source read directly — here's what's real, and where the original assumptions were wrong.

**Card Eater** (Tauri/Rust — confirms the stack choice in Section 2/16 is already the Suite convention, not just a good idea): a pure ingest-and-verify copier, nothing more. It keeps its own private SQLite database, `card-eater.sqlite3`, in its own app-data directory — **not** a shared Suite database. Relevant tables: `jobs` (source card label/path, event name, dates, status), `job_destinations` (destination path, resolved path, file/byte counts, status), and `job_files` (original name, new name, size, `hash_source`/`hash_dest`, verified flag, error). Every copied file gets a BLAKE3 hash computed on both the source and destination copy, specifically for post-copy integrity verification — this doubles as a perfectly good content checksum for Spyglass's own dedup logic, but it only exists for files that have gone through a completed copy job. Card Eater does **not** persist duration, camera model, or resolved creation date per file — EXIF-based dates are resolved transiently for naming templates and discarded, not stored. No shot segmentation, no content tags. **Adapter implication**: Spyglass's Card Eater adapter opens `card-eater.sqlite3` read-only and joins `job_files`/`job_destinations`/`jobs` to register a `clips` row per successfully-copied-and-verified file, using `resolved_path` and `hash_source` (BLAKE3) directly — no guessing needed, no write access to Card Eater's database required. Since this file is a live target of Card Eater's own async job queue, the adapter follows the concurrency contract in Section 19.3 (busy-timeout, retry-on-`SQLITE_BUSY`, fresh read connection per scan) rather than holding one connection open across a scan — **WAL mode is not actually in play here** (see Section 19.3's correction: `db.rs` never enables it), so that contract matters more than this plan originally assumed, not less.

**Built (Phase 1), verified 2026-07-24**: `crates/spyglass-core/src/adapters/card_eater.rs`, exactly this join, with the busy-timeout/retry/fresh-connection contract implemented and unit-tested against a fixture database.

**Local Interview Transcriber** (Python — Streamlit UI in a pywebview window, mlx-whisper + optional pyannote diarization, fully local): writes one JSON sidecar per video, `<video_path>.ivt-cache.json`, **next to the source file** — exactly the sidecar pattern discussed as an option for Spyglass itself in Section 9. Schema: `path`, `name`, `video_size`, `video_mtime`, `speakers` (list), `segments` (list of `{start, end, text, speaker, avg_logprob, no_speech_prob}` — Whisper's own per-segment confidence scores, a ready-made quality signal), `speaker_labels` (user-assigned display names for raw speaker IDs), and `excluded_speakers` (speakers the user chose to hide from output). Cache validity is keyed on `(file size, mtime)`, not a content hash, so it can't be used for Spyglass's own change-detection — Spyglass still needs to compute its own BLAKE3 for that. SRT/VTT/TXT exports exist but are on-demand, not written automatically alongside the cache. **Adapter implication**: walk watched roots for `*.ivt-cache.json`, and when mapping `segments` into `transcript_segments`, respect `excluded_speakers` (don't import segments for a speaker the editor explicitly hid) and apply `speaker_labels` (use the display name, not the raw diarization ID) — and carry `avg_logprob`/`no_speech_prob` through as a ready-made low-confidence flag rather than reinventing one.

**Built (Phase 1), verified 2026-07-24**: `crates/spyglass-core/src/adapters/transcriber.rs`, unit-tested including the exclusion/label-mapping behavior.

**B-Roll Analyzer** (Python/Tkinter): this is the one place the original assumption was flatly wrong. **It does not do subject-matter tagging or object/scene detection at all.** It scores technical quality only — sharpness (Laplacian variance), exposure, and stability (optical flow) — plus an optional "energy" score (exciting vs. calm, via zero-shot CLIP against two fixed prompt sets, not open-vocabulary classification). It finds each clip's best technical-quality segment(s) by sliding a scoring window across it — these are "best-quality windows," not scene-cut shot boundaries, and don't substitute for Spyglass's own shot segmentation. Its cache, `.broll_analyzer_cache.json`, is written per-folder (inside the analyzed folder), keyed on `(path, size, mtime)` — same no-content-hash caveat as the Transcriber. Its own export is a hand-built Final Cut Pro XMEML v5 file (`xml_export.py`) — this matters directly for Section 14 below. **Adapter implication**: this contributes zero rows to Spyglass's `tags` table. What it *is* worth pulling in: a technical-quality score and an energy score per clip, surfaced as numeric facets ("technical quality," "high energy") on the `shots` they overlap, rather than shoehorned into the tag vocabulary. The actual subject-matter tagging job (Section 6's gap-fill VLM pass) now carries all of the semantic-tag load, not just the gaps left by B-Roll Analyzer — it was never a semantic tagger to begin with.

**Correction found while building the adapter (2026-07-24)**: `.broll_analyzer_cache.json` only stores the settings-independent raw per-frame samples (`sharpness`, `exposure`, `motion_mag`, `motion_jitter`, `energy`) — not a precomputed technical-quality/best-window score, which B-Roll Analyzer deliberately recomputes on load (`rescore_clip`) since those depend on settings (window length, energy weight) that can change without invalidating the cache. Spyglass's adapter (`crates/spyglass-core/src/adapters/broll_analyzer.rs`) aggregates its own `technical_quality_score`/`energy_score` per shot from those raw samples instead of reading a stored score — same weighting constants B-Roll Analyzer itself uses (0.40 sharpness / 0.25 exposure / 0.35 stability), so "technical quality" means the same thing in both apps' vocabularies without depending on its code. Unit- and integration-tested.

**Bonus finding relevant to Section 14**: Rough Cut Studio already has a working `xml_builder.py` (XMEML v5, including B-roll overlay tracks with per-clip audio ducking) and an `otio_builder.py`. Combined with B-Roll Analyzer's separate `xml_export.py` doing the same XMEML v5 format independently, there are already *two* bespoke XML writers in the Suite. Section 14's "worth flagging" open question is resolved by this: Spyglass shouldn't write a third one from scratch.

Each of the three source apps is read from where its data actually lives — Card Eater's own SQLite file, the Transcriber's per-video JSON sidecars, B-Roll Analyzer's per-folder JSON cache — rather than any of them writing into a database Spyglass owns. Alongside that, Spyglass's own **watched-root scanner** (Section 7) independently walks whatever folders you point it at and feeds the same Ingestion Adapter Layer directly — so indexing never depends on every file having passed through Card Eater, the Transcriber, or B-Roll Analyzer first, and Spyglass never needs write access to another app's data (consistent with the read-only-by-contract posture in Section 8).

## 5. Data Model

Spyglass's own SQLite database (`spyglass_index.sqlite`), private to Spyglass, stored in its own app-data directory (e.g. `/Users/cj/Developer/Blair/Spyglass/data/spyglass_index.sqlite`, or the OS-appropriate app-data location once packaged — see Section 19.4 for the repo's own location) — not because any other app writes into it. Section 3's verification confirmed none of the three upstream apps keeps a shared database: Card Eater has its own private SQLite file, the Transcriber and B-Roll Analyzer keep JSON sidecars/per-folder caches. So this is Spyglass's index and Spyglass's alone, populated entirely by read-only adapters pulling from each app's existing store — a better fit for Section 8's read-only-by-contract posture than the original shared-DB design would have been, since Spyglass never needs write access to another app's data at all.

| Table | Key columns | Purpose |
|---|---|---|
| `clips` | id, file_path, source_app (`card_eater`/`spyglass_scan`), checksum (BLAKE3), size_bytes, duration, ingested_at | One row per physical media file. `checksum` is Card Eater's own `hash_source` when the file came through it, or freshly computed by Spyglass (same BLAKE3 algorithm, for consistency) otherwise. `duration` comes from Spyglass's own probing during shot detection — Card Eater doesn't persist it. |
| `shots` | id, clip_id, start_tc, end_tc, keyframe_path, technical_quality_score, energy_score, caption | Sub-segments within a clip (scene-cut level), the actual unit search returns. The two score columns are nullable and populated only when B-Roll Analyzer's cache covers that clip — numeric facets, not tags (see Section 3). `caption` (added Phase 3) holds the gap-fill VLM's raw caption text, so search results can show *why* a shot matched and a human can sanity-check an auto-tag against it. |
| `transcript_segments` | id, clip_id, start_tc, end_tc, speaker, text, avg_logprob, no_speech_prob | Sourced from the Transcriber's `.ivt-cache.json` sidecars (respecting `excluded_speakers`/`speaker_labels`); the confidence columns are Whisper's own scores, reused as-is rather than reinvented. Full-text indexed (SQLite FTS5) for keyword fallback. |
| `tags` | id, shot_id, label, source (`human`/`spyglass_vlm`), confidence | Entirely Spyglass's own doing — human corrections or the gap-fill VLM pass (Section 6). None of the three upstream apps contribute subject-matter tags. Unique on `(shot_id, label)` (added Phase 4) so a human confirming a tag the VLM already produced is a no-op, not a duplicate. |
| `embeddings` | id, shot_id, kind (`visual`/`caption`), vector | Nearest-neighbor search is a brute-force cosine-similarity scan in Rust, not the `sqlite-vec` extension originally planned here — see Section 16's corrected entry for why. |
| `collections` | id, name, shot_ids | User-created shortlists ("Fall Sports Promo cuts") — a nice-to-have but cheap to add given the schema. Backs the pool tray as of Phase 4 (a single default row, not yet multiple named collections). |
| `watched_roots` | id, label, path, volume_id, access_level, approved_by, approved_at, last_scanned_at | The allowlist of drives/folders the app is permitted to scan and index — see Section 8. |
| `clips.frame_rate` | *(column added Phase 4, not a new table)* | The sidecar now probes `cv2.CAP_PROP_FPS` alongside `duration_sec` — needed for correct Premiere XMEML frame math (Section 14), which this plan hadn't accounted for a source until it was actually being built. |
| `gap_fill_jobs` | id, clip_id, status, attempts, last_error, queued_at, updated_at | *(table added Phase 2)* The persisted background queue Section 7 calls for — one row per clip needing gap-fill, not spelled out as its own table in the original data model. |

Shot-level (not just clip-level) granularity matters here: a single ten-minute raw card dump might contain three usable shots and seven seconds of someone's thumb over the lens. Search results need to point at the specific 4-second range, not "somewhere in this clip." Note this is a different unit than B-Roll Analyzer's "best segment(s)" (its highest-technical-quality windows) — the two can overlap but aren't the same concept; Spyglass runs its own scene-cut pass regardless of what B-Roll Analyzer has or hasn't covered.

## 6. Ingestion & Gap-Fill Pipeline

Media reaches this pipeline two ways: reactively, from the three source apps' own output, or proactively, from Spyglass's own watched-root scanner (Section 7) discovering files on its own. Both paths converge on the same steps below.

1. **Discover**: three concrete, verified adapter mechanisms, plus the watched-root scanner: (a) open Card Eater's `card-eater.sqlite3` read-only and query `job_files`/`job_destinations`/`jobs` for completed, verified copies; (b) walk watched roots for `*.ivt-cache.json` sidecars sitting next to video files; (c) walk watched roots for `.broll_analyzer_cache.json` files (one per analyzed folder); (d) the watched-root scanner itself (Section 7) for anything not covered by (a)-(c). All four are periodic/event-driven scans keyed off path + mtime (Card Eater's own hash for (a); Spyglass's own BLAKE3 for (c)/(d), since neither the Transcriber's nor B-Roll Analyzer's cache includes a content hash), so re-runs are idempotent and cheap.
2. **Normalize**: each of the three adapters maps its source's actual schema (Section 3) into rows in `clips`, `transcript_segments`, `shots` (for B-Roll Analyzer's score columns), and nothing into `tags` (none of the three produce subject-matter tags). Files discovered directly by the watched-root scanner with no adapter data available get a bare `clips` row and flow straight into gap-fill. This adapter layer is the only piece that needs rework if one of the three apps changes its storage format.
3. **Shot boundary detection**: for any clip lacking shot-level segmentation already (effectively all of them — none of the three upstream apps produce true shot boundaries; B-Roll Analyzer's "best segments" are quality-selected windows, not scene cuts), run local scene-cut detection (e.g. `PySceneDetect` over `ffmpeg`) to split into `shots` and extract one keyframe per shot. Where a B-Roll Analyzer best-segment overlaps a detected shot, its technical-quality/energy scores get attached to that shot row.
4. **Visual embedding**: run every keyframe through a local CLIP model (open_clip, ONNX or PyTorch, CPU or GPU) to get a visual embedding — this is what makes "mascot cheering" match a photo that was never manually tagged "mascot."
5. **Gap-fill captioning/tagging**: run a compact local vision-language model (e.g. Moondream2 or similar CPU/GPU-local VLM) on every shot to generate a short caption and candidate subject-matter tags. This isn't filling gaps left by an upstream tagger — it's the only source of subject-matter tags in the whole pipeline, since Section 3 confirmed none of the three apps produce them.
   **Built (Phase 3), verified 2026-07-24**: moondream2, but loaded directly via `transformers` (MPS + fp16 on this Mac, ~1s/question after model load), not the `moondream` pip package — that package's client defaults to Moondream's own *cloud* API and its "local" mode still routes through the same client tied to an `api_key`, which conflicts with this Suite's no-cloud-API mandate. `transformers` is pinned to `4.44.2`; moondream2's `trust_remote_code` model code isn't compatible with newer major versions. See `sidecar/analyze_clip.py`.
6. **Text embedding**: embed transcript segments and generated captions/tags with a local sentence-embedding model so text-based semantic matching (not just keyword) works against interview content too. The Transcriber's own `avg_logprob`/`no_speech_prob` scores carry through unchanged as an existing confidence signal, rather than Spyglass computing its own.
   **Scoped down in the actual build (Phase 3)**: captions are embedded with CLIP's own text encoder — the same model already loaded for step 4 — into the same joint space as visual embeddings, rather than adding a second, separate sentence-embedding model. Transcript segments are not separately embedded; transcript-text matching still runs through FTS5 keyword search (already built in Phase 1) as one term in the hybrid score (Section 12). Reduces the sidecar's dependency footprint; revisit if search quality on transcript-heavy queries ever needs the finer-grained semantic match a dedicated text embedding would add.
7. **Write-through**: all of the above lands in Spyglass's own SQLite database — nearest-neighbor search is a brute-force cosine scan in Rust, not `sqlite-vec` (see Section 16's corrected entry). Indexing runs as a background job with a visible progress indicator (per the Suite's media-processing standard of always showing progress on long-running work), and is checkpointed so it can resume after interruption.
   **Built (Phase 2), verified 2026-07-24**: `crates/spyglass-core/src/pipeline.rs` + `src-tauri/src/gap_fill_worker.rs` — concurrency-limited, idle/pause-gated, checkpointed via the `gap_fill_jobs` table (see Section 5's corrected table list).

## 7. Watched Roots & Background Indexing

This is the direct answer to "so I don't have to manually process everything": Spyglass doesn't need footage to have passed through Card Eater, the Transcriber, or B-Roll Analyzer first. Point it at a folder — a whole archive drive, a single season's footage, whatever — and it independently discovers and fully processes everything inside on its own.

**Configuration**: a "Watched Folders" settings panel where you add/remove root paths. Each root is scanned recursively; a configurable extension allowlist (`.mov`, `.mp4`, `.mxf`, etc.) filters out non-media files, and a few sensible exclusions are on by default — render/proxy subfolders, hidden files, and specifically the two known sidecar filenames from Section 3 (`*.ivt-cache.json` next to videos, `.broll_analyzer_cache.json` inside analyzed folders) so they're read as adapter input, never mistaken for footage themselves.

**Dedup against existing metadata**: before treating a discovered file as brand new, the scanner checks it against `clips` by checksum and path. If Card Eater or another app already has a record for it, the scanner merges rather than duplicates — it only fills in whatever that record is missing (no shots yet? run shot detection. No tags? run gap-fill). If there's no existing record at all, the file is registered fresh with `source_app = spyglass_scan` and runs the full pipeline end to end.

**Background job queue**: discovered files are queued rather than processed inline, with a configurable concurrency limit (respecting CPU/GPU headroom) and a policy to pause automatically when the machine is under active editing load and resume at idle — consistent with the Suite's "never block an active edit" requirement. The queue is persisted, so quitting the app or losing power mid-scan just means it picks back up on next launch.

**Progress and error handling**: the settings panel shows live status per watched root — files discovered, indexed, queued, and failed (e.g., "14,820 / 15,000 indexed, 180 queued, 12 failed — view errors"). Failures (corrupt files, unreadable codecs, permission issues) are logged and skipped rather than halting the batch; a "retry failed" action re-attempts them without a full rescan.

**Re-scanning**: watched roots are periodically re-walked (and can be manually triggered with a "Re-scan now" button) to catch newly added footage. Because discovery is checksum/mtime-based, a re-scan of a folder with 50,000 already-indexed files and 200 new ones only touches the 200 — it doesn't reprocess anything already done.

## 8. Access Scope & Permission Controls

Yes — and this should be the default posture, not an optional lockdown mode. By default Spyglass has zero filesystem visibility: no drive or folder is scanned, indexed, or even peeked at for a file count until it's explicitly added to an allowlist. This isn't just a UI convention that a bug could route around — every disk access the app makes (folder walk, checksum read, frame extraction, thumbnail write, "reveal in Finder," export path resolution) is checked against the current allowlist at the I/O layer itself, so there's no code path that reaches outside approved roots even if something upstream is broken.

**Allowed Roots table** — a new `watched_roots` table, added to the Section 5 data model:

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `label` | Human-readable name shown in the UI (e.g. "Fall Sports Archive — Drive 3") |
| `path` | Mount path at time of approval |
| `volume_id` | Stable volume UUID/serial number — not just the mount path, since drive letters and mount points shift between reconnects |
| `access_level` | `active` (indexed, searchable, reveal/export enabled) · `paused` (stays searchable, no new scanning) · `removed` (indexed content purged) |
| `approved_by` / `approved_at` | Who granted access and when — matters if more than one editor ends up using the Suite |
| `last_scanned_at` | Feeds the per-root status panel from Section 7 |
| `sidecar_cache_enabled` | Off by default; a separate opt-in permitting the app to write a mirrored cache alongside media on this root — see Section 9 |

**Permission controls**:

- **Explicit opt-in, never auto-discovery.** Plugging in a new drive doesn't trigger a scan. An unrecognized volume shows up in Settings as "detected, not yet approved," and needs an explicit "Add to Spyglass" action before anything on it is touched. Because this is effectively granting a broad read-scope, it's the kind of action worth a confirmation dialog rather than a silent default.
- **Volume identity, not just path.** Roots are keyed to the volume's UUID/serial rather than its mount path. A drive that reconnects at a different path is still recognized as the same approved root — and, just as importantly, a different drive that happens to remount at an old path like `/Volumes/Archive` is never silently treated as trusted just because the path matches.
- **Read-only by contract, with one explicit, opt-in exception.** By default, Spyglass never writes to, moves, renames, or deletes anything inside an allowed root — it only reads media and writes its own index/thumbnail cache elsewhere, in the Suite's own data folder. "Search" never implies write access to the archive itself. The one carve-out is the optional mirrored sidecar cache described in Section 9, and it requires its own separate opt-in per root rather than being implied by approving the root for indexing.
- **Pause vs. remove, treated differently.** Pausing a root stops new scanning and takes it out of active indexing, but keeps already-indexed shots searchable — useful for an archive drive that's temporarily disconnected. Removing a root purges its shots, tags, and embeddings from the index entirely; being destructive, it warrants the same explicit confirmation as any delete.
- **Enforced where the I/O happens, not just in the UI.** The allowlist check lives inside the watched-root scanner and gap-fill pipeline themselves (Section 7), not just in what folders the "Add Folder" dialog happens to show — so scope can't be bypassed by a query, an export, or a future feature that forgets to check.

## 9. Handling Intermittent External Drives

Given the archive lives on external drives that get connected and disconnected constantly, this isn't an edge case to patch around — it's the normal operating condition the design needs to assume from the start. Short answer: search stays fully usable with a drive unplugged; indexing pauses cleanly on that drive and resumes automatically when it's back.

**Search never depends on a drive being mounted.** Every shot's keyframe — the thumbnail search results actually show — is extracted once during indexing and cached inside the app's own local data folder, not read live off the archive drive on every search. So browsing, searching, and filtering work identically whether zero or all of your drives happen to be plugged in. What *does* require the drive is anything touching the original file: opening the full clip, "reveal in Finder," and the Section 12/13 exports. Results from an offline drive show a clear "offline — reconnect [Drive Name]" badge on the thumbnail rather than a broken image or a silent failure, and clear automatically the moment the app sees that volume reappear.

**Indexing treats disconnection as a pause, not an error.** Since volumes are tracked by UUID (Section 8) rather than mount path, the moment the app is notified a watched volume has unmounted — via OS-level volume notifications, not by waiting for a read to fail — any in-flight job on that volume (checksum, scene detection, embedding) is cancelled cleanly and its file re-queued as "pending, awaiting reconnect," rather than left half-written or retried against a drive that's no longer there. Everything already committed to the index before the unmount stays exactly as indexed. When the volume reappears, the scanner resumes the queue where it left off.

**Why "wait for a read error" isn't good enough.** Yanking an external drive mid-read is often messier than a clean failure — some filesystem drivers hang on I/O for a stale handle instead of erroring immediately, which would otherwise stall the entire background queue behind one dead file. Subscribing to the OS's own mount/unmount notifications (e.g. Disk Arbitration on macOS) means the app finds out proactively and can cancel in-flight jobs before a hang has the chance to happen.

**Content-based relinking.** If a drive gets reformatted and comes back with a new volume UUID, it's treated as unrecognized and needs re-approval — a deliberate safety choice from Section 8, since silently trusting a different drive that happens to reuse an old mount path is exactly the failure mode that policy exists to prevent. But because files are matched by checksum, not just by path, if the same media reappears anywhere in an approved location — the same physical drive reformatted, or copied onto a different approved drive entirely — the existing shot, tag, and embedding records get relinked to the new path instead of being reprocessed from nothing. Re-analysis only ever happens for content that's genuinely new.

**One thing worth deciding early**: whether an indexing job interrupted by a disconnect should retry immediately on reconnect, or wait for idle time. Reconnecting a drive is often exactly the moment you're about to start editing from it, so defaulting to "wait for idle" avoids the scanner competing with you for disk I/O right when you need it most.

**Optional: mirroring the cache alongside the media.** Yes, this can be done — with a caveat worth being upfront about. If a sidecar cache written to the drive became the *only* copy of a clip's keyframes, tags, and embeddings, that would undo the point of everything above: unplugging the drive would take that content out of search entirely, and it would mean Spyglass writing to archive volumes it otherwise never touches, contradicting the read-only-by-contract rule in Section 8.

The useful version of this is a hybrid, opt-in per root: the central index in the app's own data folder stays the single source of truth for search — that's what makes cross-drive queries and offline browsing work at all — but a watched root can optionally also get a mirrored sidecar cache written alongside the media (a hidden `.spyglass/` folder per clip, holding its keyframe images plus a small JSON manifest of shot boundaries, tags, transcript segments, and embeddings).

The real payoff isn't offline search — the central cache already covers that — it's disaster recovery and multi-machine consistency. If the app gets reinstalled, the central index is lost or corrupted, or the drive is handed to a different edit bay, re-scanning that drive rehydrates from the sidecar instead of re-running the expensive part of the pipeline (scene detection, embeddings, and especially VLM captioning) from scratch. Checksums decide which copy wins if the two ever disagree; the sidecar is a backup of the derived data, never an alternate source of truth.

What it takes to support: `watched_roots` (Section 8) gets a `sidecar_cache_enabled` flag, off by default and toggled per root — a separate, explicit opt-in from just approving the root for indexing, since writing to the drive is a genuine exception to that section's "never writes to an allowed root" rule and deserves its own confirmation dialog spelling out exactly what gets written and where. On a fresh scan, the pipeline checks for an existing sidecar before running gap-fill — found and checksum-matched, it rehydrates instead of re-analyzing; missing or mismatched, it analyzes normally and writes a fresh one if the root has this enabled.

## 10. Cache Footprint & Size Controls

Fair concern, worth pinning down with real numbers rather than a vague reassurance.

**Where the size actually comes from.** Overwhelmingly, keyframe images. A CLIP visual embedding is a few kilobytes at most (512 floats, ~2KB at full precision, well under 1KB quantized); a shot's tags, transcript text, and shot-boundary metadata add up to well under a kilobyte more. A keyframe thumbnail sized for search results — say 480px on the long edge at moderate JPEG quality — runs roughly 25-40KB, an order of magnitude bigger than everything else about that shot combined. In practice keyframes are on the order of 90% of the cache footprint; the SQLite index (embeddings, text, FTS5) is the rest.

**Rough sizing**, using ~35KB per shot fully loaded (already includes overhead): a season's footage indexed at around 10,000 shots comes to roughly 350MB. A multi-year archive at 100,000 shots lands around 3.5GB. Even a genuinely huge archive at 500,000 shots is around 17.5GB. Worth plugging in your actual clip count once you have a feel for it, but at these per-shot costs, a cache that stays in the tens-of-gigabytes range even for a very large archive is the expected outcome — and the settings below give direct control if it ever needs to be smaller than that.

**Levers that actually keep it small**:
- **Keyframe resolution and quality is the one setting that matters most.** A thumbnail only needs to be good enough to recognize a shot in search results, not archival quality — capping it around 480px with moderate JPEG compression rather than storing a full-resolution frame accounts for most of the size control on its own.
- **Quantize embeddings.** Storing vectors as int8 rather than float32 cuts that (already small) share of the footprint roughly 4x, with negligible impact on ranking quality — a standard trade-off in vector search generally, nothing specific to this app.
- **Treat keyframes as regenerable, metadata as permanent.** Tags, transcripts, shot boundaries, and embeddings are what search actually runs on, and they're cheap enough to keep indefinitely. Keyframe images exist purely to render a thumbnail and can always be re-extracted from the original file when the source drive is mounted — so they're the one thing safe to evict under space pressure without losing any search capability, just momentarily losing the thumbnail until it regenerates (or showing a generic "reconnect to view" placeholder in the meantime).
- **A configurable cache size cap with LRU eviction.** A setting like "keep cache under 10GB" that, once hit, evicts the least-recently-viewed keyframes first — never the embeddings, tags, or transcripts — and regenerates them on demand the next time that shot surfaces in a search with its source drive connected.
- **Relocatable cache folder.** School edit machines sometimes run small internal boot SSDs, so the app's local data folder shouldn't be hardcoded to the system drive — letting it live on any internal or fast external volume keeps the cache from competing with OS and application storage.
- **The sidecar option (Section 9) interacts with this directly.** If per-root sidecar mirroring is enabled, that archive drive already holds a full copy of its own keyframes — so the central cache can be pruned more aggressively for that content, since a durable copy exists to regenerate from even without re-reading the original video file.

**Settings panel**: a simple breakdown (keyframes vs. index/embeddings vs. transcripts) with current size, a size cap slider, and a "Clear keyframe cache" action that's safe and reversible (thumbnails just regenerate next time they're viewed) — kept clearly distinct from "Remove root" (Section 8), which is destructive and triggers full re-analysis.

## 11. Multi-User Handoff

Yes — and the simplest version of this falls straight out of the local-first design already in place, no new architecture required. What doesn't come automatically is *shared, live-synced* state between two installs, which is worth being upfront about before assuming that's what "the same way" means.

**Independent-copies model (the default)**: hand the coworker the app and access to the same physical archive — a shared/network-visible drive both machines can reach, or the actual external drives changing hands. They go through the same Section 8 approval flow on their own machine, with their own `watched_roots` allowlist and their own confirmation dialogs — nothing skipped just because these drives were already approved on your install, since that opt-in is deliberately per-install, not global. Their local cache builds out from there, and once indexed, their experience is identical to yours: same search, same UI, same exports — just backed by their own local SQLite/cache rather than a shared one.

**This is exactly where sidecar caching (Section 9) pays off.** If sidecar mirroring is enabled on the archive drives, a coworker's fresh install doesn't need to re-run the expensive part of indexing (scene detection, embeddings, VLM captioning) — it finds the sidecars on first scan and rehydrates from them, turning what could be hours or days of reprocessing on a large archive into a fast relink. Without sidecars enabled, their first index build is a full one, same as yours originally was.

**Exportable allowlist, for convenience only.** A "share my approved roots" export from Section 8's `watched_roots` table can pre-fill the coworker's list of drives/paths so they're not reconstructing it from memory — but each entry still needs its own explicit confirmation on first use there. Pre-filling isn't the same as auto-trusting; that would undercut the explicit-opt-in principle the whole permission model is built on.

**What doesn't come for free: shared, live state.** Two independent installs mean two independent indexes. If a coworker corrects a tag or builds a pool/collection, it lives in their local database only — it won't show up on your machine, and vice versa, unless you manually reconcile. For a two-person team where that drift is a real problem, the alternative is a shared, network-reachable index both installs query against — but that's a materially bigger piece of architecture, not a checkbox. SQLite over a network share (SMB/AFP) is known to be unreliable under concurrent writers, since file locking on network filesystems is exactly the kind of thing that causes silent corruption — so a genuinely shared index would mean standing up a small local network service rather than pointing two installs at one file, a real departure from the "one person, low-maintenance, no standalone servers to babysit" constraint from Section 2. Worth treating as a deliberate later decision if a second full-time editor genuinely needs live-shared state, rather than building it preemptively.

## 12. Search & Query Layer

A single internal query API that the desktop UI calls, taking a query object like `{ text?, facets?, referenceShotId?, dateRange? }` and returning ranked shots:

- **Semantic text search**: embed the query text with CLIP's text encoder, run nearest-neighbor search over `visual` and `caption` embeddings (brute-force cosine similarity in Rust — see Section 16's corrected sqlite-vec entry); merge with a hybrid score.
- **Facet search**: plain SQL filter over `tags`/`clips` (category, date range, source event) — fast, exact, good for browsing rather than describing.
- **Visual similarity**: embed a reference keyframe, nearest-neighbor over `visual` embeddings, excluding the reference shot itself.
- **Hybrid ranking**: weighted fusion of vector similarity score, tag exact-match boost, and FTS5 keyword match on transcripts — so a query like "coach interview about the mascot" can pull from transcript keyword hits and visual similarity at once.
- Results always carry `clip_id` + `start_tc`/`end_tc` so "open at this point" and "send to timeline" are trivial.

**Built (Phase 3/4), verified 2026-07-24**: `crates/spyglass-core/src/search.rs` (`search_shots` for the text-query path, `find_similar_shots` for visual similarity — both implemented and covered by an end-to-end integration test using a real gap-filled clip and a real query embedding, not a mock). **Facet search built, verified 2026-07-26**: `crates/spyglass-core/src/facets.rs` — `list_facet_options` (tag/source counts, ingested-date bounds), `matching_shot_ids` (OR within a facet category, AND across categories), `browse_shots` (facet-only, no text query, newest-ingested-first), and `search_shots` now takes a `FacetFilters` param so a text query and facets combine (Section 2's "combined/hybrid search" bullet). Scope note: only `tags.label`, `clips.ingested_at`, and `clips.source_app` have real columns behind them — this section's original "source event" and "shot type" facets have no data source anywhere in the pipeline and aren't built; see `facets.rs`'s own doc comment for what each would take.

## 14. Selection Pool → Premiere Pro XML Export

Yes — this is straightforward to build, and it reuses the `collections` table already in the data model rather than adding new plumbing.

**How it works**: `collections` becomes the backing store for the pool tray — each pool is a `collections` row holding an ordered list of `shot_id`s (each already carrying its `clip_id`, `start_tc`, and `end_tc`). Exporting a pool walks that ordered list and generates a single XML file that Premiere Pro imports as a bin containing a sequence, with each shot placed back-to-back at its correct in/out points.

**Format specifics**: Premiere Pro does not read Final Cut Pro X's native `.fcpxml` format directly — that requires a third-party converter (e.g. XtoCC). What Premiere *does* read natively, and has for years, is the legacy XMEML format (the XML dialect from Final Cut Pro "Classic" 7, which Adobe extended with its own tags). Since Spyglass is generating this file from scratch rather than converting someone else's export, this isn't a real constraint — it just means the exporter's target format is XMEML (sequence spec version 5), not FCPXML.

**What the exporter needs to get right**:
- Absolute, correct file paths to the original source media (Premiere resolves clips by path on import; broken paths mean an offline-media relink step for you later).
- Matching frame rate and timebase per clip, since mixed frame rates across archive footage (a real possibility over multiple years of cameras) need to be handled per-clip rather than assumed constant.
- In/out points expressed in the same timecode base Premiere expects (frame-accurate, not just seconds), pulled straight from each shot's `start_tc`/`end_tc`.
- A clean, human-editable sequence/bin name (e.g. pool name + export date) so it's identifiable once it lands in the Premiere project panel.

**Rough flow**: pool tray → "Export to Premiere Pro" → write `.xml` to a chosen local folder → Premiere Pro: File > Import > select the XML → a new bin appears with the assembled sequence, ready to drop onto a timeline for finishing.

**Decided**: Rough Cut Studio already has a working `xml_builder.py` producing this exact XMEML v5 format, including B-roll overlay tracks with per-clip audio ducking, plus an `otio_builder.py` for OpenTimelineIO. B-Roll Analyzer independently has its own `xml_export.py` doing the same XMEML v5 format a second time. Rather than Spyglass becoming a *third* bespoke XML writer from nothing, Spyglass ports the proven logic — frame rate/timecode math, per-channel audio routing, the overlay/lane-assignment approach — into its own Rust codebase, generated from its own `resolved_segments` list built out of pool shots. It treats `xml_builder.py` and `xml_export.py` as reference implementations to port from, not code to call into or modify: no import, no shared runtime dependency, and no changes to either sibling app's files, consistent with Section 19's scoping decision. Extracting one real shared library across all three apps stays on the table as a later, explicit, opt-in refactor — not something this build does on its own. The same approach applies to Section 15 below.

**Built (Phase 4), verified 2026-07-24**: `crates/spyglass-core/src/xmeml.rs`. Ported the load-bearing details the two reference files got right the hard way: every clipitem's in/out/duration computed at the *sequence's* frame rate (never a source clip's native rate, even when they differ — confirmed in the references against a real Premiere import, where mixing rates produces an "insufficient media" error); stereo audio split into one mono clipitem per channel on separate tracks (a single multichannel clipitem silently imports as mono); `<link>` elements binding video+audio clipitems together; `<file>` definitions deduplicated by real source path. Built as a bare `<sequence>` (matching `xml_builder.py`'s shape, not `xml_export.py`'s fuller `<project>/<bin>` wrapper) via hand-templated strings with a small XML-escape helper, rather than a new XML-writing library dependency. The generated output is parsed by a real XML reader in tests to catch tag-nesting mistakes substring checks alone would miss. One scope note, resolved in Phase 5: audio was originally emitted as a fixed stereo/48kHz/16-bit assumption per clip rather than the source's real probed format — Phase 5 added `ffprobe.rs` and wired each clip's real channel count/sample rate/bit depth in here, including a mono source correctly getting one audio track instead of a fabricated silent second channel (see Section 15's build note).

## 15. Consolidate & Copy Export

A second pool export mode, sitting right alongside the Premiere XML handoff: physically copy — optionally trimmed — everything in the pool into one self-contained destination folder. This covers cases the XML export doesn't: archiving a finished project's source material, handing footage to an outside editor or vendor without giving them the whole archive, or building an offline copy that doesn't depend on the archive drives staying mounted.

**Trigger**: the same pool tray as the Premiere export (Section 14) — "Export to Folder" sits next to "Export to Premiere Pro" as a second action on the same staged selection.

**Copy modes**:
- **Full source clip**: copies the entire original file untouched. No re-encode, no frame-accuracy risk, preserves all original metadata and audio — but can be far larger than needed if only a few seconds of a long clip were selected.
- **Trimmed to shot (+ handle)**: copies only the selected in/out range plus a configurable handle (default around a second) for retrim flexibility later. Two implementation paths, worth surfacing as a real trade-off: stream copy (`ffmpeg -c copy`) is fast and lossless but snaps to the nearest keyframe, so the actual start point can drift from the requested in-point depending on the source's GOP structure; a full re-encode is frame-accurate but slower and re-compresses the footage. Given the pool likely mixes codecs from years of different cameras, defaulting to stream-copy-with-handle and only re-encoding where the source's keyframe spacing makes that imprecise is the more scalable default — but this should be a visible, per-export setting, not a silent decision, since it matters whether footage got recompressed.

**Folder structure & naming**: flat by default, with an optional "subfolder per tag/collection" layout for exports that feed straight into a labeled delivery. Because camera-generated filenames repeat constantly across a multi-year archive (`C0001.MP4` from a dozen different shoots), copied files are renamed on the way out — e.g. `{pool_name}_{sequence}_{original_basename}` — rather than relying on original names staying unique at the destination.

**Manifest**: every export writes a companion CSV/JSON alongside the copied media — one row per file, with original path, copied path, in/out points used, tags, and checksum. This is what makes a folder handed to an outside vendor self-documenting on its own, and it's also what lets the exporter optionally generate a *second* Premiere XML pointing at the newly copied files instead of the original archive paths — useful for building an edit that doesn't require the archive drives to stay mounted.

**Safety before copying starts**: a destination free-space check against the estimated export size (warn rather than fail partway through a multi-hundred-gigabyte copy), a collision check if the destination folder isn't empty, and — since this is a genuine "writes new data" action rather than a read-only search — an explicit confirmation step showing file count, total size, and destination before anything is written.

**Integrity verification**: checksum each copied file against its source once the copy completes, cheap insurance against a flaky cable or NAS connection corrupting a multi-gigabyte file mid-transfer; flag mismatches in the manifest rather than assuming success.

**Progress and resumability**: same pattern as indexing (Section 7) — visible per-file and overall progress, checkpointed so an interrupted export resumes rather than restarting from the first file.

**Built (Phase 5), verified 2026-07-24**: `crates/spyglass-core/src/consolidate.rs` — both copy modes (full-source `std::fs::copy`; trimmed via ffmpeg, stream-copy with `-ss` before `-i` or re-encode with `-ss` after `-i` for genuine frame accuracy, a real trade-off exposed as a visible per-export setting rather than decided silently); collision-safe renaming (`{pool_name}_{sequence:03}_{original_basename}`); flat or subfolder-per-tag layout (a shot with multiple tags lands under its first tag, not duplicated into every tag's folder — a deliberate Phase 5 scope call, not an oversight); a companion CSV+JSON manifest (original/copied path, in/out, tags, BLAKE3 checksum, `checksum_verified`) checkpointed to disk after *every* file, not just at the end, which is also what makes resumability work — a re-run skips any destination file that still matches its manifest checksum rather than restarting from file one; pre-export destination free-space (via `df`) and non-empty-folder checks; the paired "XML pointing at copied files" export (`manifest_to_xmeml_clips`, reusing `xmeml.rs` rather than a second writer). `crates/spyglass-core/src/ffprobe.rs` — real per-clip audio format (channels/sample rate/bit depth) via ffprobe, built once and shared by both this export and a corrected `xmeml.rs` (Section 14's fixed stereo/48kHz/16-bit assumption is now each clip's own probed format, with a mono source correctly getting one audio track instead of a fabricated silent second channel). Tauri commands (`estimate_consolidate_export`, `start_consolidate_export`, `get_consolidate_export_status`, `export_copied_files_to_premiere_xml`) run the copy on a plain background thread with a polled status slot in `AppState`, matching this app's existing polling pattern rather than introducing push events for one feature. Frontend: `ConsolidateExportModal.tsx`, an options → confirm (file count/size/free-space/collision warnings) → progress → done flow, with "Export to Folder" sitting next to "Export to Premiere Pro" in the pool tray. Verified for real, not just mocked: real ffmpeg-synthesized clips through real ffprobe (mono/stereo, differing sample rates) and a real ffmpeg stream-copy trim producing a smaller playable file, both `#[ignore]`d by default per this repo's convention for tests depending on local ffmpeg/ffprobe on PATH. 93 total tests passing (89 unit + 4 real-integration, all green with `--include-ignored` on this machine).

## 16. Trade-offs and Open Decisions

- **sqlite-vec vs. a standalone vector DB (Chroma/LanceDB) — decided, then corrected once actually building it.** The original call was sqlite-vec: everything in one file, no extra service to run or back up. **Correction found 2026-07-24**: the official `sqlite-vec` Rust crate (`sqlite-vec = "0.1.10-alpha.4"`) fails to build in this environment — confirmed via a standalone probe, its packaged source is missing a bundled file (`sqlite-vec-diskann.c`), a real bug in that alpha release, not something fixable from the consuming side. Nearest-neighbor search is instead a brute-force cosine-similarity scan implemented directly in Rust (`crates/spyglass-core/src/search.rs`), which is fast enough for a "press enter to search" UI at this plan's own stated archive scale (tens of thousands of shots — see below, "revisit past ~1M" still applies) and meaningfully simpler/more reliable than depending on an experimental extension. Revisit sqlite-vec if that crate matures, or once the archive grows past roughly a million indexed shots and query latency becomes a problem either way.
- **CLIP-only vs. adding a captioning VLM**: CLIP embeddings are fast and fully local but weaker on fine-grained actions ("cheering" vs. "clapping" vs. "waving"). The gap-fill captioning pass adds real indexing time but meaningfully improves recall on action-based queries — worth it given search quality is the whole point of the app.
- **Shot-level vs. clip-level granularity**: shot-level (with scene-cut detection) is more indexing work up front but is what actually makes results useful — pointing an editor at "somewhere in this 12-minute card dump" isn't a real answer to a search query.
- **Auto-tag confidence**: model-generated tags will sometimes be wrong. Store a `source` and `confidence` per tag rather than overwriting anything, and surface low-confidence tags differently in the UI (or exclude them from facet browsing until confirmed) so bad auto-tags don't quietly pollute search quality.
- **Shared DB vs. per-app DBs with adapters — decided, not just defaulted into.** The original draft of this plan proposed one shared SQLite file all four apps write into. Reading the actual code (Section 3) showed none of the three upstream apps has a shared-DB write path today, and retrofitting one would mean modifying Card Eater, the Transcriber, and B-Roll Analyzer's actual persistence code — which runs straight into this repo's own standing convention (see the Suite-level `CLAUDE.md`) that every sibling app must keep working as a fully standalone tool, and that changes to a sibling's internals need an explicit per-incident go-ahead, not a default architecture choice. A shared DB would also mean Card Eater's copy job (async Tokio queue), the Transcriber's deliberately single-threaded pipeline (a documented workaround for Metal/MPS quirks), and B-Roll Analyzer's process pool all safely writing to one target — three different concurrency models with no upside to any of them individually from being coupled together, plus a much larger blast radius (a shared-write bug or lock contention issue now affects all four apps at once, versus one malformed sidecar just being skipped under the current model) and a standing cross-app migration contract for a solo maintainer to keep honoring on every future schema change. The instant-consistency benefit a shared DB would buy doesn't offset that: nothing in this plan calls for true real-time sync, and the watched-root scanner's periodic re-scan already delivers "shows up in search within a reasonable delay." Read-only adapters win on every axis that matters here — this section stays as the record of why, not just what.
- **OS-level unmount events vs. simple polling — decided differently once Card Eater's own precedent was checked.** This plan originally favored Disk Arbitration-style notifications over polling. Reading Card Eater's actual `volume_watcher.rs` (Section 3-style verification) showed it deliberately chose plain `/Volumes` polling instead, for exactly this reason: card-insert detection doesn't need millisecond responsiveness, and polling avoids a new dependency/Objective-C bridge. Spyglass's own volume watcher (Phase 2, `src-tauri/src/volume_watcher.rs`) follows that same precedent — it polls each *active* watched root's own path for reachability (not a generic `/Volumes` diff, since Spyglass only cares about its own approved roots). What actually solves this bullet's real concern (cancelling an in-flight job *before* a stale file handle hangs) is a separate, more targeted mechanism: a shared cancel-token registry (`InFlightRegistry`) that the volume watcher signals the instant it notices a root go offline, killing that root's in-flight sidecar subprocess directly rather than waiting out a timeout. Polling frequency and proactive-cancellation are two different problems; this build solved the one that actually mattered with a smaller, more targeted piece than a full Disk Arbitration integration.
- **Tauri vs. Electron**: Tauri's native-webview architecture gives a far smaller footprint per app — which compounds across an eight-app Suite in a way it wouldn't for a single standalone tool — and its capability-based permission model maps naturally onto the explicit-opt-in allowlist from Section 8. The cost is a Rust backend instead of Node, mitigated by keeping Rust to the native shell/OS-integration layer and running the CLIP/VLM pipeline as a Python sidecar process rather than porting it to Rust. (Confirmed as the right call, not just a guess — Card Eater is already built this exact way: Tauri shell, Rust core.)
- **Reuse existing XMEML builders vs. writing a new one — decided: port, don't extract.** Rough Cut Studio's `xml_builder.py` and B-Roll Analyzer's `xml_export.py` already solve this exact problem (frame rate/timecode math, per-channel audio routing that Premiere's XMEML import is picky about), and a genuine shared library would avoid the three ever drifting apart on edge cases each one already learned the hard way. But extracting one means editing files inside both sibling app directories, which this repo's own `CLAUDE.md` gates behind your explicit, per-incident go-ahead — not something a plan document gets to pre-authorize. So Spyglass ports the logic into its own Rust code instead, treating the two existing builders purely as reference implementations. This accepts a small amount of duplicated logic (and the risk of the three drifting on some future edge case) in exchange for touching neither app. A real shared library stays available as a later, explicitly-approved refactor if that duplication ever becomes a real maintenance problem.

## 18. What to Revisit as the Archive Grows

Watch for: sqlite-vec query latency as embedding count climbs (mitigate with approximate NN indexing or migrating to a dedicated vector store); indexing throughput if new footage volume outpaces idle-time processing (mitigate with a priority queue — most-recently-ingested and most-likely-to-be-needed-soon content indexed first); tag taxonomy drift as auto-tagging generates an ever-growing set of near-duplicate labels (periodic taxonomy cleanup pass, deduping "cheering" vs. "cheer" vs. "cheering on"); and whether independent per-install indexes (Section 11) are still good enough once a second full-time editor is actively using the Suite day to day — that's the point where a shared, network-reachable index stops being a "maybe someday" and becomes worth the added operational complexity.

## 19. Before Handing to Claude Code

A short, concrete checklist — closing these out is what actually makes Phase 1 buildable, more so than anything already resolved above.

1. **Decided — XMEML: port, don't extract, touch neither sibling app.** Phase 4 ports the XMEML-writing logic (frame rate/timecode math, per-channel audio routing) into Spyglass's own Rust code, using Rough Cut Studio's `xml_builder.py` and B-Roll Analyzer's `xml_export.py` purely as reference implementations — no import, no shared runtime dependency, no edits to either app's files. This is now the plan of record (Sections 14/16), not just a default pending approval. Extracting a real shared library across all three apps stays available as a later, separately-approved refactor if the duplication becomes a real problem — it is not pre-authorized by this plan and Claude Code should not start it without you asking for it specifically.
2. **Decided — standalone now, embeddable later.** Spyglass is built and shipped as its own standalone Tauri app, matching Card Eater's precedent and fitting cleanly into Studio Suite's pattern of Tauri apps living outside the Python-mixin wrapper. To keep a later embed genuinely possible rather than a rewrite, Spyglass's core logic (indexing pipeline, adapters, search/query API) should live in a Rust library crate separate from the Tauri-shell binary, with a stable local API boundary (in-process calls for the standalone build; the same crate callable from, or the same API reachable by, a future Studio Suite integration) — the concrete mechanism for that future embed (linking the core crate directly vs. Studio Suite's wrapper pointing at a locally-served Spyglass UI) is a decision to make when that day actually comes, not now. What matters for this build is simply not entangling business logic with standalone-window-specific glue, so nothing has to be torn apart later to make the embed happen.
3. **Decided — read strategy against Card Eater's live database.** All four of the following together, not a choice between them; each solves a different part of the same problem:
   - **~~Confirm `card-eater.sqlite3` is opened in WAL mode~~ — checked, and it isn't.** This plan assumed Card Eater "almost certainly" already runs WAL for its own job queue's sake. Reading `db.rs` directly (2026-07-24) shows it does not — `Connection::open` runs with the default rollback-journal mode, no `PRAGMA journal_mode=WAL` anywhere in the codebase. WAL isn't a property Spyglass's read-side adapter can impose either, so this isn't fixable from Spyglass's side even if it wanted to be. Practical effect: the three items below (which don't depend on WAL) are what actually carry this contract, and Card Eater write contention is somewhat more likely to surface as a transient busy read than this plan originally assumed — the retry logic exists precisely for that case, so nothing about the contract itself needed to change once this was known, just the confidence level behind assuming it away.
   - **Spyglass's adapter sets `PRAGMA busy_timeout`** (on the order of 1-2 seconds) on its own read connection, so a brief write in progress is waited out automatically instead of failing on first contact.
   - **Retry-on-`SQLITE_BUSY`** as the outer safety net: one or two retries with a short backoff if a wait ever exceeds the busy-timeout, then skip that file for this scan pass and pick it up on the next one, rather than aborting the whole indexing job over one transient lock.
   - **Open a fresh read connection per scan** (open → query → close) rather than holding one open for the adapter's lifetime. Under WAL, a long-held read transaction would block the write-ahead log from ever checkpointing back into the main file; under Card Eater's actual rollback-journal mode a long-held reader can instead block or be blocked by a writer entirely, which is if anything a stronger reason to keep connections short-lived, not a weaker one.
   
   Net effect: Spyglass never causes a Card Eater write to fail, and Card Eater's own activity essentially never causes a failed Spyglass scan — worst case, one pass skips a still-busy read and catches it next pass. This is the concrete implementation contract for the Card Eater adapter in Section 3/6, and it's what's actually built there (Phase 1, verified 2026-07-24) — not left for Claude Code to discover through an intermittent "database is locked" bug.
4. **Decided — repo location: `/Users/cj/Developer/Blair/Spyglass`**, a sibling of `Rough Cut Studio Suite/` itself rather than a folder inside it — so Spyglass lives alongside the Suite, not nested among `CardEater/`, `B-Roll Analyzer/`, etc. This doesn't change anything about the governance rule in Section 19.1: that rule is scoped to the five sibling app directories *inside* `Rough Cut Studio Suite/`, and Spyglass living next to that folder rather than in it has no bearing on whether Claude Code may touch Rough Cut Studio's or B-Roll Analyzer's own files (it still may not, without your explicit go-ahead).

Lower-priority, safe to leave to Claude Code's judgment rather than block on: exact model/library pinning (which open_clip checkpoint, which VLM) and per-phase acceptance criteria — both easy to adjust once Phase 1 is underway and real behavior is visible.
